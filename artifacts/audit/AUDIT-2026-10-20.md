# Ember Finance OS — product, engineering, and production audit

Audit date: 20 October 2026. Context: a personal finance app for USD client payments into NSave, conversion into BDT, local spending, giving, subscriptions, bills, and saving.

## Verdict

Ember has a useful application structure and a recognizable visual identity. It is an operational prototype with significant correctness and durability gaps. It should not yet be the sole source of truth for personal finances or be exposed publicly without access protection. The most urgent work is protecting the ledger, making transfers and sync reliable, and correcting financial calculations. A full visual rewrite is unnecessary.

## Coverage and evidence

- Read all nine application pages, the shared layout, dashboard widgets, settings components, store, synchronization layer, both financial rules engines, database schema, three API handlers, seed generator, and project configuration.
- `npm run lint` passed. This script runs TypeScript only; it does not run ESLint.
- `npm run build` passed, including prerendering the application routes.
- `npm audit --omit=dev --json` reported zero known production dependency vulnerabilities at audit time. This does not assess application-level security.
- Inspected all nine pages in a separate Chromium session at 1440px, 768px, and 390px, using the production build. Captured screenshots and layout measurements.
- Reproduced eight financial/storage cases with an in-memory localStorage substitute and blocked network calls.
- Browser requests to all `/api/*` routes were intercepted with synthetic data. The isolated production preview had database and AI integrations disabled. No real financial records were read, created, reset, or deleted through these checks.
- Live deployment access controls, live Neon schema/data, backup retention, external AI responses, real account statements, and real-device performance were not verified. API issues below are established from source unless explicitly described as reproduced.

Evidence: [finance results](finance-results.json), [browser results](browser-results.json), [finance reproduction script](verify-finance.ts), [browser inspection script](browser-audit.mjs). Scripts are diagnostic artifacts; the browser script uses this machine's cached automation library and browser path.

## Release blockers: protect the ledger first

### F01 — Critical: the database API has no application authentication or ownership checks

**Evidence:** `src/app/api/db/route.ts:16`, `:115`, `:350`; `src/lib/db/schema.ts`.

GET reads all account and transaction data. POST accepts a ledger payload and writes it. DELETE clears tables and the server snapshot. No handler checks a session or owner identity. The schema has no owner scope. The AI handlers are also unauthenticated.

**Impact:** if the deployment is reachable without an external access gate, another visitor can read financial information, change it, or invoke deletion. A private database connection string does not protect the HTTP API. A UI confirmation on the reset button does not protect the endpoint.

**Fix:** for this personal app, enforce an authenticated, allowlisted owner on every API handler, including AI routes. Verify any deployment-level gate separately. If multi-user access is introduced later, add ownership columns and scope every query. Do not build a complex public sign-up system merely to secure a single-owner app. Next.js explicitly advises treating route handlers as public API endpoints and checking authorization there: [authentication guidance](https://nextjs.org/docs/app/guides/authentication).

### F02 — High: browser and database transfer contracts are incompatible

**Evidence:** `src/types/index.ts:50`, `src/app/accounts/page.tsx:121`, `src/app/api/db/route.ts:52`, `:211`, `src/lib/finance.ts:124`.

The browser creates and calculates with `amountOutMinor` / `amountInMinor`. The database API writes and returns `fromAmountMinor` / `toAmountMinor`. Neither boundary maps these names correctly.

**Reproduced:** a database-shaped USD 100 transfer with a USD 5 fee should leave USD 895 from USD 1,000 and credit BDT 12,000. The client calculated USD 995 and credited BDT 0. On upload, the handler supplies undefined values for the database's required transfer amount columns, leading to the write-error fallback.

**Fix:** choose one canonical transfer contract, validate it, map database rows explicitly, and test its browser → API → database → API → browser round trip.

### F03 — High: normal deletions never reach PostgreSQL

**Evidence:** `src/lib/store.ts:80`, `src/lib/sync.ts:42`, `src/app/api/db/route.ts:122`.

Deleting a transaction/account/budget removes it from browser storage. Sync only inserts or updates the remaining records. It never deletes missing database records. On a later cloud pull, deleted rows can return.

**Fix:** represent deletes explicitly, using authenticated delete mutations or versioned tombstones. Test deletion across refresh and a second browser. Whole-ledger reset is not a substitute for ordinary deletion semantics.

### F04 — High: database errors can be reported as successful sync after partial writes

**Evidence:** `src/app/api/db/route.ts:122`, `:324`, `:336`; `src/components/layout/Header.tsx:62`; `src/components/settings/DataManagement.tsx:94`.

The API writes records one at a time without a database transaction. If a later write fails, earlier writes remain; the API then writes a JSON file and returns success. The browser may say “Cloud Synced” or “Auto-Sync to Neon Active” even when the actual provider is the server file fallback. Idle is also displayed as synced.

**Impact:** a later healthy database GET can return older or partial data, replacing the newer browser/file copy. The UI provides more assurance than the storage state supports.

**Fix:** make related writes atomic, fail visibly when the authoritative store is unavailable, and display the actual persistence provider and dirty/sync/error state. Treat a separate backup as a backup rather than a silent change of primary database.

The fallback writes under `process.cwd()/.data`. This needs explicitly durable storage on a persistent server and is unsuitable as written for standard Vercel Functions, whose documented filesystem is read-only except scratch space: [runtime filesystem documentation](https://vercel.com/docs/functions/runtimes#file-system-support). This app has no durable-volume configuration in the repository.

### F05 — High: startup can overwrite offline edits or mix demo records into real data

**Evidence:** `src/components/layout/AppShell.tsx:15`, `src/data/seed.ts:25`, `src/lib/sync.ts:96`, `src/lib/store.ts:24`.

Startup seeds sample records before pulling cloud data. Every seeded write schedules upload. If cloud loading is slow, a sample snapshot can upload first. Cloud pulls replace local collections without checking for unsynced changes, versions, or conflicts. Two browsers/tabs have no conflict protocol.

**Fix:** load an explicit initialization state first; restore authenticated data before enabling writes; make demo mode a separate, opt-in workspace. Preserve pending local operations and resolve version conflicts. For a small personal app, a server-authoritative ledger with a browser cache may be simpler than full offline synchronization.

### F06 — High: valid browser state does not survive a full database round trip

**Evidence:** `src/app/api/db/route.ts:65`, `:271`, `:318`; `src/lib/db/schema.ts:81`, `:102`, `:123`.

Budget `month: '2026-10'` is ignored during POST, which writes `period: 'monthly'`. GET maps that literal back into `month`, so it no longer matches the dashboard's month filter. Exchange rates and user settings are included in sync payloads but never written by POST; settings are never returned by the database GET. Category parent relationships are also omitted. Insight records are not part of the synced ledger.

**Fix:** define explicit mappings for every persisted entity, migrate the database to match the actual domain, and verify export/import and sync round trips. The existing tables alone do not establish persistence support.

## Financial correctness and daily-use reliability

### F07 — High: mismatched transaction/account currencies corrupt balances

**Evidence:** `src/app/transactions/page.tsx:151`, `:639`; `src/app/subscriptions/page.tsx:83`; `src/lib/finance.ts:109`.

The UI independently selects currency and account. Balances subtract the raw transaction amount without conversion or currency validation.

**Reproduced:** starting with USD 1,000, recording a BDT 1,200 expense against that account produces USD -200. At an example rate of 120, an explicitly converted charge would instead deduct USD 10. The current model cannot represent both the purchase amount and actual account debit.

**Fix:** default to and enforce account currency. If foreign-currency card purchases are needed, store both purchase currency/amount and the actual settlement currency/amount. Validate subscription funding accounts the same way. Ensure category type also matches income/expense after switching form tabs; the selected category state can currently retain an incompatible ID.

### F08 — High: month/date calculations shift in Bangladesh

**Evidence:** `src/lib/finance.ts:147`, `:189`; `src/app/subscriptions/page.tsx:54`; `src/lib/rules-engine.ts:68`; `src/data/seed.ts:16`.

The app constructs a local first-of-month date, then extracts a UTC ISO month. Dhaka midnight is still the previous day in UTC.

**Reproduced:** the October six-month chart shows April–September instead of May–October. At 00:30 on 1 November in Dhaka, the transaction default based on UTC becomes 31 October. Historical baseline windows and seed dates share this pattern.

**Fix:** distinguish calendar dates, local reporting months, and UTC timestamps. Store financial dates as `YYYY-MM-DD` calendar values and calculate reporting periods consistently in the configured timezone. Use UTC for actual timestamps, not to derive local calendar labels.

### F09 — High: transfers affect balances but are absent from the main ledger and cash-flow fee totals

**Evidence:** `src/app/accounts/page.tsx:134`, `:143`; `src/app/transactions/page.tsx:78`; `src/lib/finance.ts:124`, `:167`, `:318`.

Transfers live in a separate collection. Account history and transaction CSV read only transactions. Transfer fees reduce source balances, but monthly expenses and savings calculations do not include them.

**Reproduced:** a USD 5 transfer fee reduces the account correctly while monthly reported expenses remain zero. Excluding the transfer principal from income/expenses is appropriate; omitting its fee is not.

**Fix:** expose transfers as linked ledger events and represent fees consistently as expenses without counting the principal as spending. Include them in account history and provide a complete export. Add transfer correction/reversal support; the store currently has only create/get methods for transfers.

### F10 — High: budgets from different months are counted together

**Evidence:** `src/app/budgets/page.tsx:72`, `:155`; compare `src/lib/finance.ts:244`.

The Budgets page iterates all saved budgets but applies this month's spending to each. If the same category has September and October budgets, both limits appear and October spending can be counted twice in the summary. The dashboard filters by month, so the two screens disagree. Parent category budgets do not include their child category spending.

**Fix:** select the reporting month explicitly, filter once before all calculations, offer an intentional copy-to-next-month action, and define parent/child roll-up rules. Apply linear daily pacing to variable spending; fixed rent due at the start of a month needs a due-date-aware presentation.

### F11 — High: goal balances are unverified manual counters

**Evidence:** `src/app/goals/page.tsx:86`, `:169`, `:309`; `src/types/index.ts:84`.

“Contribute” increments `currentMinor` without recording a source account, moving money, or reserving funds. Multiple goals can claim more than the account balances. “Total Reserves Accumulated” implies funded money that the app has not verified. Those amounts also do not reduce spendable funds or runway.

**Fix:** support reservations within an existing account and actual transfers to a dedicated savings account as distinct actions. Link allocations to funds, track allocation changes, cap reservations against available money where appropriate, and keep net worth unchanged by internal allocations. If progress remains manually self-reported, label it that way.

### F12 — High: runway and health can be extremely reassuring with insufficient data

**Evidence:** `src/lib/finance.ts:182`, `:281`; `src/app/dashboard/page.tsx:90`.

The runway denominator is an all-history average over months that contain expenses, rather than the documented three-month baseline. With no expenses it falls back to one minor currency unit per month. The synthetic browser fixture displayed **241,667 months of runway and health 100/100** with no spending history.

**Fix:** show “Not enough expense history” until a useful baseline exists, use a documented period with consistent treatment of empty/partial months, and distinguish liquid available reserves from total account balances. Show score inputs and data completeness; make targets configurable for irregular freelance income.

### F13 — High: subscription burden has multiple inconsistent definitions

**Evidence:** `src/lib/finance.ts:308`, `:466`; `src/lib/rules-engine.ts:94`; `src/lib/golden-rules.ts:215`; `src/app/coach/page.tsx:163`.

The subscription metrics helper normalizes yearly/quarterly/weekly cycles. The dashboard health calculation and basic rules engine sum raw billing amounts. The coach's own calculation handles yearly and quarterly but omits weekly normalization.

**Reproduced:** a USD 120 annual subscription correctly appears as USD 10/month in normalized metrics but the rules engine calls it USD 120/month. This can produce contradictory assessments across pages.

**Fix:** use one calculation function and one documented income baseline everywhere. Treat the threshold as a user-adjustable budget preference rather than a universal safety boundary.

### F14 — High: the AI coach sends cents as dollars

**Evidence:** `src/app/coach/page.tsx:149`, `:173`, `:179`; `src/app/api/ai/coach/route.ts:29`, `:150`.

`convertToUsd` returns USD minor units. The page sends these as `incomeUsd`, `expenseUsd`, and `amountUsd`; the API prints them directly as dollars. A USD 1,000 income becomes USD 100,000 in the prompt and deterministic review. Ratios can remain plausible while monetary explanations are wrong by 100×.

**Fix:** retain explicit `UsdMinor` names across internal and API contracts and convert only when formatting. Validate returned AI objects before rendering them. Label the response source so deterministic fallback is distinguishable from remote AI output.

### F15 — Medium: subscription renewals can duplicate expenses and drift dates

**Evidence:** `src/app/subscriptions/page.tsx:83`.

“Record Renewal” creates a new transaction on every invocation, then separately advances the due date. There is no subscription-period payment identity or duplicate check. Native `setMonth` can move a 31 January due date into March instead of the end of February. The type supports weekly billing but renewal advancement omits it. Upcoming dashboard subscriptions are sliced in storage order rather than sorted by due date.

**Fix:** link payment to subscription and billing period, make recording idempotent, permit editing an incorrect payment, and calculate recurrence from an explicit billing anchor with month-end rules. Show overdue/due-soon status and source-account funding.

### F16 — Medium: historical reports change when today's reference FX rate changes

**Evidence:** `src/lib/finance.ts:68`, `:169`, `:189`; `src/app/reports/page.tsx:53`, `:285`.

Historical income/expenses are translated using the current global rate. Actual transfers do retain their own rates, which is useful, but reports mix these two meanings. Average realized rate is an unweighted mean over all transfers, including same-currency movements. The report labels every transfer as USD out / BDT in and prints every fee with `$`, even though the transfer form permits reverse and same-currency transfers.

**Fix:** separate present-day portfolio valuation from historical cash flow. Preserve original amounts and reporting-rate provenance. Derive effective USD→BDT rates from actual amounts received/sent and show weighted averages only for compatible conversions. Use actual account and fee currencies in labels. The `timeRange` state in Reports is unused; the report always shows the computed six-month series.

### F17 — Medium: 50/30/20 classification depends on exact category names

**Evidence:** `src/lib/finance.ts:519`; `src/lib/golden-rules.ts:136`.

Anything outside a hardcoded Needs list becomes Wants, including the seeded Savings category and potentially essential work subscriptions or family commitments. When spending exceeds income, the denominator switches to spending, concealing the percentage of actual income consumed.

**Fix:** give categories explicit user-configurable budget groups; distinguish savings transfers, essential business tools, living costs, giving, and discretionary spending. Display overspending as a deficit rather than normalizing it away.

## Product design, interaction, and trust

### F18 — High: the shared modal styles are missing

**Evidence:** all entry forms use `modal-overlay` and `modal-content`; neither class is defined in `src/app/globals.css`. Example: `src/app/transactions/page.tsx:517`.

**Observed:** Add Activity renders an ordinary `position: static` block below the ledger. In a short synthetic ledger it began at y≈612px and extended beyond the 1000px viewport. With many rows it can be much farther below the fold. There were zero dialog elements/roles.

**Fix:** implement a shared dialog or intentionally visible drawer with viewport positioning, scrolling, labeling, focus entry/return, keyboard dismissal, and background focus isolation. Preserve incomplete form input where appropriate. [W3C's dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) describes the expected keyboard and focus behavior. Evidence: [transaction entry screenshot](transaction-form-1440.png).

### F19 — High: desktop dashboard layout does not adapt to mobile

**Evidence:** `src/app/dashboard/page.tsx:137`, `:166`, `:172`; `src/app/globals.css:635`; `src/components/layout/AppShell.tsx:58`.

The stylesheet hides the sidebar at a breakpoint but does not reflow the dashboard's fixed two-/three-column grids. Main padding remains 36px per side.

**Observed:** at a 390px viewport, dashboard document width was **642px**. The cash-flow chart is squeezed while the 340px health column runs outside the viewport; lower cards remain in cramped columns. Subscriptions reached 421px and Coach 400px, partly from long unwrappable guide controls. Tables in Transactions and Reports have internal scrolling; offscreen table cells alone are not evidence of document overflow.

**Fix:** stack dashboard groups on phones, use `minmax(0, 1fr)` for flexible tracks, reduce phone gutters, allow guide labels to wrap or shorten them, and prioritize amount/account/status in mobile ledger rows. Evidence: [mobile dashboard](dashboard-390.png), [desktop dashboard](dashboard-1440.png).

### F20 — Medium: the default background competes with the financial content

**Evidence:** `src/app/globals.css:31`, `:45`; background defaults in `src/lib/background.ts:65`.

**Observed:** the top of the default flame image is bright gold behind white page headings, navigation, helper text, and translucent controls. Small muted labels and red expense text are difficult to read in several areas. The dark lower cards are much easier to scan. This is a visible readability finding, not a formal measured WCAG contrast certification.

**Fix:** retain the ember identity as a restrained accent; use a strong dark scrim and more opaque working surfaces. Keep important amounts, labels, and controls readable across every allowed background and brightness setting. Make a quiet/static workspace the default or a prominent option.

### F21 — High: privacy and encryption claims contradict implementation

**Evidence:** `src/components/settings/SystemManual.tsx:31`, README privacy section, `src/lib/store.ts:27`, `src/lib/sync.ts:54`, `src/app/coach/page.tsx:163`.

The manual says data remains encrypted in localStorage and no data goes to external cloud servers. Records are plain JSON. Sync uploads them automatically. Coach automatically requests remote review, and natural-language parsing can forward raw text and account/category names to Google when configured.

The `aiCoachEnabled` / `shareAiDetails` preferences exist in types but are not enforced in the calling pages or handlers. **Observed:** with `aiCoachEnabled: false`, visiting Coach at three tested widths still produced three `/api/ai/coach` requests. They were intercepted during the audit, so no external AI received the fixture.

**Fix:** provide accurate storage/sharing copy, make external AI explicitly optional, honor preferences at both boundaries, and send only necessary fields. Remove the encryption claim unless application-level encryption is implemented with a real key-management design. “Local-first” does not mean encrypted or local-only.

### F22 — High: cloud pulls do not refresh the visible page

**Evidence:** `src/lib/sync.ts:112`; pages generally read localStorage once in mount effects; no shared ledger-change subscription exists.

**Reproduced:** cloud response changed an account name. Storage contained `CLOUD PULLED ACCOUNT`, but the mounted Accounts page still showed the older name. Dashboard and other snapshots use the same pattern. The background system already has an event subscription pattern, while the money store does not.

**Fix:** introduce one observable application store or query cache, hydrate it deliberately, and invalidate derived calculations after mutations and cloud updates. Support `storage` events for cross-tab changes if browser storage remains part of the architecture.

### F23 — High: failed browser writes are silently treated as successful actions

**Evidence:** `src/lib/store.ts:24`, `:63`, `:71`.

**Reproduced:** forcing a storage quota error caused `createTransaction` to return a created transaction, even though re-reading storage showed it was absent. Page handlers close their forms regardless. Uploaded wallpaper data shares the browser's storage budget.

**Fix:** return or throw actionable persistence errors, keep the form open, display a recoverable message, and distinguish local persistence from remote persistence. Validate loaded/imported data instead of treating corrupt JSON as an empty financial history.

### F24 — Medium: backup export exists, restore does not

**Evidence:** `src/components/settings/DataManagement.tsx:23`; `src/lib/store.ts:175`.

Settings downloads a JSON archive but exposes no upload/restore flow. `store.importAll` is an internal function, not a user recovery workflow. CSV serialization does not escape embedded quotes and does not neutralize formula-leading text. Transfers are absent from CSV.

**Reproduced:** merchant `Client "Alpha"` generates an improperly escaped CSV field; note `=1+1` remains a spreadsheet formula candidate. [OWASP's CSV injection guidance](https://community.owasp.org/attacks/CSV_Injection) explains the spreadsheet behavior.

**Fix:** provide validated, versioned restore with a preview, record counts, replace/merge choices, automatic pre-restore backup, and transactional application. Escape CSV correctly and protect text cells from formula interpretation. Test restoring into an empty workspace and comparing balances, transfers, budgets, and preferences.

### F25 — Medium: reset/demo controls do not match their promises

**Evidence:** `src/components/settings/DataManagement.tsx:48`, `:60`; `src/data/seed.ts:25`; `src/app/api/db/route.ts:350`.

Seed Demo calls a function that immediately returns when already seeded, while showing a success toast. It does not perform the advertised replacement. Reset removes the seed flag and reloads, causing sample data to be created again. The DELETE handler can suppress database-clear errors and still return success, and does not clear exchange-rate/settings tables.

**Fix:** separate “empty personal workspace” from “demo workspace”; preserve the selected mode across reloads; verify delete results; require successful reset completion before reporting it. Keep demo actions away from normal data management once real records exist.

### F26 — Medium: account edits and deletes can invalidate history

**Evidence:** `src/app/accounts/page.tsx:65`, `:93`; `src/lib/store.ts:99`; `src/lib/db/schema.ts`.

An account's currency can be changed after activity exists. Existing minor-unit amounts are then interpreted in the new currency. Deleting an account leaves its transactions/transfers/subscriptions referring to a missing account, and its balance disappears from portfolio totals. The schema does not enforce the relevant foreign keys.

**Fix:** make account currency immutable after posting entries; archive accounts with history; offer controlled correction of opening balances with an effective date; define explicit handling of related records. Add database reference and validity constraints.

### F27 — Medium: accessibility and form feedback need a shared implementation

**Evidence:** `src/components/layout/MobileNav.tsx`; transaction/account/goal forms; `src/components/settings/BackgroundCustomizer.tsx:82`; `src/app/globals.css:498`.

Mobile navigation lacks dialog/focus/escape handling and an accessible close name. Many field labels are visually adjacent but not associated with inputs. Some icon actions are only 24–26px. Background presets are clickable divs without keyboard semantics. Invalid submissions often silently return; AI parse failures only log to the console. The mobile global Add button has no text label once desktop-only text is hidden.

**Fix:** shared field/dialog/icon-button primitives; explicit label associations and error messages; keyboard-operable preset buttons; practical touch targets; accessible names for icon controls; announced saving/error states. Page guides should expose expanded state and controls relationships.

### F28 — Medium: production hydration errors remain

**Evidence:** six React error #418 events during production browser inspection, recorded in `browser-results.json`. `CurrencySettings` initializes from browser storage during render; Coach calculates financial content during render with different server/browser data.

React identifies error #418 as a server/client hydration mismatch: [official error reference](https://react.dev/errors/418). The app's extension-warning filters and `suppressHydrationWarning` do not resolve application data differences. Exact attribution of each of the six events was not recorded by the diagnostic script.

**Fix:** provide a consistent server snapshot or a deliberate loading state until browser hydration completes; centralize storage subscriptions. Remove broad error-suppression workarounds after isolating actual extension-specific issues. The current root script also installs a document-wide mutation observer and suppresses errors matching broad text such as `M_ID`, which can hide useful diagnostics.

## Product direction for this user's actual workflow

The main job is: “When a client pays me, show what I can convert, what is already committed, and what I can safely spend locally.” The existing pages contain pieces of that job but require manual interpretation.

| Workflow | Recommended product behavior |
| --- | --- |
| Receive USD | Record the client payment to NSave, payment date, actual credited amount, and any fee; client/project and invoice references can stay optional |
| Allocate income | Apply user-chosen fixed amounts or percentages to giving, upcoming bills, savings, and local living funds; keep allocations as reservations rather than invented expenses |
| Convert into BDT | Record actual USD debit, actual BDT credit, fee amount/currency, source/destination, transaction date, and pending/settled state; derive effective rate and preview both resulting balances |
| Spend locally | Fast entry with BDT account preselected, recent categories/payees, appropriate numeric keyboard, and reliable undo/correction |
| Pay recurring bills | Show upcoming obligations, account, due date, amount, funding gap, and whether that period is already paid |
| Give money | Separate planned giving, reserved giving, and actual payments; track zakat and sadaqah separately if the user wants both |
| Review | Reconcile account balances against statements, inspect uncategorized entries and overdue bills, and close a month with a stable record |

Giving needs a dedicated model, not just a category renamed “charity.” A user-chosen income percentage can create a sadaqah/giving reserve. Zakat should have a separately defined review period, calculation inputs, adjustments, and payment record if supported. The app should not assume an income percentage and a zakat calculation mean the same thing. This is a software modeling recommendation, not a determination of religious obligations.

The first dashboard viewport should prioritize:

1. Available BDT for everyday spending after relevant reservations and upcoming obligations.
2. USD held in NSave, with the reference conversion estimate clearly labeled.
3. Giving reserved / paid / remaining for the selected period.
4. Bills due soon and whether their accounts are funded.
5. This month's income, spending, and an inspectable surplus calculation.

Keep net worth, charts, and coaching below those decisions. Move visual atmosphere controls below currency, privacy, backup, and account controls in Settings. Replace phrases like “granular journal,” “capital injections,” and “amortized monthly deposit requirements” with “Transactions,” “Add to goal,” and “Save this much each month.” Preserve useful navigation, currency formatting, category drill-downs, manual input, and the ember color identity.

## Engineering direction

Use one canonical, runtime-validated domain model at storage and API boundaries. Keep explicit units in names. Centralize selectors for balances, monthly cash flow, normalized recurring costs, and reporting periods, then share them across Dashboard, Coach, and Reports.

For this personal product, choose one authoritative persistence strategy. An authenticated PostgreSQL ledger with browser caching and an explicit pending-operation queue is likely easier to reason about than silent full-snapshot replacement among localStorage, PostgreSQL, and a server JSON file. If robust offline use is a requirement, design operation versions, idempotency, deletion tombstones, and conflict handling before calling sync dependable.

Strengthen TypeScript incrementally (`strict` is currently false), remove `any` from persistence mappings, and give money/currency/date contracts real validation. Add foreign keys and validity constraints, durable migrations, appropriate owner/date indexes, and atomic ledger operations. PostgreSQL money fields currently use 32-bit integers; review whether the roughly BDT 21.47 million major-unit ceiling is acceptable before storing larger aggregate amounts.

The project has no committed automated test suite or CI workflow. High-value tests are transfer conservation and fee handling; currency/account compatibility; Dhaka date boundaries; budget month isolation; subscription recurrence/idempotency; sync/delete/conflict behavior; and backup/restore equivalence. Avoid spending the first testing effort on cosmetic component snapshots.

Performance risk comes from repeated full-array localStorage parsing inside conversion helpers, nested balance calculations, and sequential per-row uploads of the full ledger on every change. This was not a load test; desktop compilation speed is not runtime performance evidence. Compute from a single in-memory snapshot and persist mutations efficiently. The continuously running sparks canvas still executes when CSS hides it for reduced motion; gate its animation loop and pause unnecessary background work. Prefer locally hosted/subset fonts over a CSS Google Fonts import if privacy and predictable loading matter.

Production operation also needs verified database backup/restore, release migrations, error reporting that excludes private financial payloads, structured sync failure reporting, an LTS runtime pin, and a reproducible CI build. The audit host used Node 26 alpha and npm emitted a compatibility warning; this is an environment finding, not a demonstrated application failure. No production runtime pin is committed.

## Recommended fix order and acceptance criteria

| Order | Work | Acceptance criteria |
